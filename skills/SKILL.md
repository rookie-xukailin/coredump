# Coredump 智能分析 Skill

## 何时使用

用户提供 coredump 文件（core、core.gz、tar.gz 包）时，自动触发本 skill。

## 工作流程

### 第 1 步：运行 bmccore 分析

```bash
# 找到 bmccore 工具（根据实际部署位置调整）
BMCORE_DIR="${BMCORE_DIR:-/tmp/coredump_work/proj}"

# 全量分析（需要符号表目录 + 源码树）
python3 ${BMCORE_DIR}/bmccore.py analyze <core文件> \
    --symbol-table <符号表目录> \
    --source-root <源码树> \
    [--console-log <串口日志>] \
    [--offline] \
    -o /tmp/bmccore_report
```

如果用户没有指定符号表/源码树，先询问。

### 第 2 步：读取结构化报告

```bash
# 优先读 JSON（结构化，便于程序化提取）
cat /tmp/bmccore_report/*_report.json
# 同时读 Markdown（人读格式，含源码片段）
cat /tmp/bmccore_report/*_report.md
```

### 第 3 步：深入源码分析（本 skill 的核心增量）

bmccore 报告告诉你"哪里崩了"，你要在此基础上结合源码告诉用户"为什么崩"和"怎么修"。具体做法：

#### 3a. 读取崩溃帧的完整函数体

报告的"源码片段"只贴了 ±5 行。你需要：
1. 从报告 JSON 提取所有 `file:line` 对
2. 找到源码树中对应文件
3. **读取整个函数体**（从函数声明到闭括号）
4. 分析崩溃行的上下文：变量来源、调用链、资源持有状态

#### 3b. 分析根因（按崩溃类型分类）

| 崩溃类型 | 报告特征 | 你要做的深入分析 |
|---|---|---|
| 空指针 | 出错地址 < 0x1000 | 追溯指针变量的赋值链，找到"谁把它置空/没初始化" |
| 堆溢出 | 堆取证有 chunk 损坏 + 前块嫌疑 | 读前块对应的数据结构，找写入操作（memcpy/strcpy/循环赋值），判断为什么越界 |
| UAF/悬垂 | 受害对象探测 + '相邻块嫌疑' | 追溯对象的 free/释放路径和 stale 引用持有者 |
| 栈溢出 | SP 出界/保护页 | 读递归/大局部变量的代码，判断终止条件或缓冲大小 |
| 坏函数指针 | pc = 野地址 | 追溯函数指针的赋值点和被踩路径 |
| 竞态 | 多线程 + 数据被踩 | 分析线程同步原语的缺失场景 |

#### 3c. 交叉引用分析

1. **堆指纹 grep**：报告"内容指纹"给出的字符串，在源码树中 grep，找到写入这些字节的代码
2. **引用搜索**：报告"指向受害区的引用"给出的持有者，追溯其数据结构定义
3. **调用链完整性**：确认报告回溯中每个帧的函数是否真的可能互相调用（防止栈污染假阳性）

### 第 4 步：输出针对性指导报告

格式（用 Markdown）：

```markdown
# Coredump 分析报告

## 1. 崩溃概要
- 进程：xxx (pid=xxx)
- 架构：arm64/arm32/riscv64
- 信号：SIGSEGV/SIGABRT/SIGBUS/...
- 出错地址：0x...
- 崩溃点：`函数名` @ `文件:行号`

## 2. 调用链
#0 崩溃函数 @ file.c:42
#1 调用者 @ file.c:100
...

## 3. 根因分析
[结合源码的具体分析——不是泛泛的"可能是空指针"，
而是"第 42 行的 `dev->ctrl_reg = xxx` 中 `dev` 来自全局变量 `g_dev`，
该变量在 `main()` 入口处声明但从未调用 `dev_init()` 赋值，
因为初始化函数名拼写错误（`dev_ini()` vs `dev_init()`）"]

## 4. 堆取证（如适用）
- 受害对象：地址 0x...，大小 N 字节
- 踩写痕迹：'XXXX' 指纹
- 肇事嫌疑：相邻块 / 前一个 chunk
- 源码定位：指纹字符串出现在 xxx.c 的 yyy 函数

## 5. 修复建议
[具体的、可操作的修复——给出代码 diff 或伪代码]

### 建议的修复
\```c
// 文件: xxx.c
// 行 42: 添加空指针检查
if (!dev) {
    LOG_ERR("device not initialized");
    return -ENODEV;
}
dev->ctrl_reg = xxx;
\```

### 额外的防御措施
- 建议在 `main()` 入口添加初始化断言
- 考虑用 `__attribute__((nonnull))` 标注指针参数

## 6. 置信度说明
| 结论 | 可信度 | 依据 |
|---|---|---|
| 崩溃直接原因 | 确认 | 信号 + siginfo |
| 根因 | 确认/疑似 | 源码分析 + 堆取证 |
| 修复建议 | 建议 | 基于分析推断 |
```

## 关键能力对照

| 能力 | bmccore 工具 | 本 skill 增量 |
|---|---|---|
| 崩溃检测/信号归因 | ✅ 自动 | 直接使用 |
| 符号配对/回溯 | ✅ 自动 | 直接使用 |
| 栈扫描兜底 | ✅ 自动 | 直接使用 |
| 堆取证/受害对象探测 | ✅ 自动 | 直接使用 |
| 源码片段提取 | ✅ ±5 行 | **扩展到完整函数体 + 调用链分析** |
| 根因分析 | ❌ 只给线索 | **结合源码深入分析"为什么"** |
| 修复建议 | ❌ 不给 | **给出具体代码级修复方案** |
| 堆指纹源码定位 | ❌ 只给指纹 | **自动 grep 源码找到肇事代码** |
| 交叉引用 | ❌ 只给地址 | **追溯数据结构定义和持有者** |
| 多线程竞态分析 | ❌ 只给线程栈 | **分析同步原语缺失场景** |

## 注意事项

1. 不要猜测——如果源码不在 `--source-root` 指定的树中，如实说"源码不可达，无法深入分析"
2. 堆指纹可能匹配多个位置——列出所有候选，标注可信度
3. 多线程场景注意区分"崩溃线程"和"肇事线程"（报告有标注）
4. 报告的"疑似"结论表示工具的不确定性——你在源码分析后可以将其升级为"确认"或否定
5. 如果符号配对失败（missing/mismatch），提醒用户检查符号表版本
6. console 日志很重要——glibc 的 abort 原因只打印在 stderr，core 里没有

## 环境要求

- bmccore 工具目录（含 bmccore.py + bmccore/ + open/pyelftools/）
- 符号表目录（用户编译阶段产出的未 strip ELF 文件）
- 源码树（用于深入分析和修复建议）
- Python 3.8+（不需要任何 pip 依赖）
- 交叉 gdb（可选，缺失时自动降级到栈扫描）
